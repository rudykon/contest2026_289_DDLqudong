# 黄山派约 2 秒响应延迟：实板诊断

> 此文记录上一轮历史版本；当前烧录版本与进一步优化结果见 [响应优化第二轮验收](响应优化第二轮验收.md)。

2026-09-22，SF32LB525 / 390×450 / openvela + QuickApp。结论：已经在绕过触摸传感器的合成输入中复现，软件处理链路本身就足以产生接近 2 秒的延迟。此次修正了无必要的整屏重绘，但开始/停止训练及首次建页仍偏慢，不能认定已达到流畅目标。

## 1. 两个已确认的瓶颈

**按下和松开按钮也在重画整屏。** 当前 NuttX LCD 配置分配一个完整帧缓冲；LVGL 驱动据此选择 FULL 模式。一次普通翻页实测出现按下、松开、目标页面共 3 次刷新。以缓存后的首页→初筛为例，总延迟 941ms，其中刷新累计 635ms：布局 163ms、软件绘制及刷新剩余开销 392ms、LCD 同步传输 80ms。每一帧实际发送 175,500 像素。屏幕传输单次约 25–28ms，没有看到 LCD 等待超时，不能把这些长停顿归咎于面板传输。

**QuickApp 的业务与 UI 共用事件循环。** `watch_desktop.cpp` 调用 `ShellApp::Create(..., false)`，运行时非异步分支将应用放在 UI 线程。合成按压本来约 100ms 后松开，训练时实测有一次到 850ms 才开始处理松开。开始/停止操作中，`lv_indev_read()` 的同步松开事件处理分别测到 411/425ms；局部刷新对照仍有 403/380ms。它包含事件派发与相关处理，不是单独算法耗时。

源码中停止训练会在同一路径更新大量状态、生成摘要/复盘、调用保存、构造历史与导出预览。`stopSession()` 调用 `applyHistory()` 后还再次调用 `applyExportPreview()`，而前者内部已经调用了后者；这是后续应清理的重复工作，但本轮未单独测定其耗时，不能把整个延迟归因于这一次重复调用。

首次页面创建还增加了控件创建和文字布局工作：诊断中初筛、时间线、协同第一次展示时，最终一帧布局约 242–306ms，软件绘制约 177–312ms；此前还有建页和事件调度时间。字体裁剪减少的是静态存储，保留相同字形和字号不会自动消除这些布局/绘制工作。

## 4. 测量边界与复现

计时是设备端合成 LVGL 按下至页面标志变化后的刷新完成，包含约 100ms 的人工按压和其调度延误；不包含串口命令等待、真实传感器采样和面板像素响应。它不是手指到光的测量，也不能排除额外的物理触摸问题。FT6146 为中断后 HPWORK 立即排队读取，代码中没有固定 2 秒等待；本次没有重新测量真实手指到触摸中断的时延。

逐帧日志里的 `layout` 是 REFR_START 到 RENDER_START，`flush` 是同步 flush 回调持续时间，`draw` 是该次刷新扣除上述两者后的剩余时间，并非纯绘图指令的 CPU 采样。字形生成、调度和少量刷新管理开销也可能包含在内。诊断日志会产生一定额外开销，阶段对照的两轮均开启；最终复测关闭逐帧输出。

```powershell
.\benchmark-ui.ps1 -Name latency-repeat -Reset
.\benchmark-ui.ps1 -Name latency-trace -Reset -Trace
.\benchmark-ui.ps1 -Name native-repeat -Reset -NativeOnly
.\verify-latency-display.ps1
```

脚本会复位设备并运行演示训练，RAM 中原有训练记录不会跨复位保留。测试输出保存在 `logs` 和 `validation`。`analyze-latency.py <测试名...>` 重新汇总已有日志。

下一步优化重点应是把训练收尾、摘要/历史生成与非当前页更新移出关键交互路径，并验证运行时异步 JS 模式；同时减少页面重排。不能仅通过再删字库、调小字号或提高标称刷新率解决。异步模式尚未在本轮启用或验证。
