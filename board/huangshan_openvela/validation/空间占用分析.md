# 小芽快应用与黄山派固件空间分析

> 本文是精简前的历史分析，对应 9,316,168 B 固件。后续已执行字库与资源精简，最新结果见 `字库资源精简验收.md`；旧 JSON 已保留为 `size-firmware-before-font-subset.json`。

分析日期：2026-09-22。只读检查了部署 RPK、最终 ELF/链接映射、实际生成的 ROMFS，并通过 COM5 查询了实时内存；没有修改或烧录运行中的固件。

结论：**快应用安装包本身很小；整机固件主要被两套中文字库和系统运行环境占据。** Flash 精简应优先针对字库和示例资源。安装包小不等于运行开销小，交互性能仍需要优化 JS 执行与绘制。

## 1. 三种“大小”不能混在一起

| 项目 | 实际大小 | 含义 |
|---|---:|---|
| 小芽 RPK | 52,851 B / 51.61 KiB | 压缩、签名后的快应用安装包 |
| 小芽解包内容 | 178,272 B / 174.09 KiB | 当前 ROMFS 中实际部署的小芽文件，占总固件 1.91% |
| 整机固件 | 9,316,168 B / 8.885 MiB | openvela、QuickApp 运行时、图形库、字体、所有应用、原生桌面 |
| 当前系统堆已用 | 3,696,376 B / 3.525 MiB | 系统全局堆统计，不是小芽单独占用 |
| 当前系统堆可用 | 4,979,384 B / 4.749 MiB | 最大连续空闲块 4,979,248 B |

本项目固件从 `0x12010000` 写入，烧录脚本以 `0x990000`（10,027,008 B / 9.5625 MiB）作为不碰到后续 MTD 分区的上限。当前已用这个空间的 **92.91%**，剩余 **710,840 B / 694.18 KiB**。芯片全部 16 MiB Flash 的剩余空间不能直接当作固件可扩展空间。

电脑上的 `nuttx` ELF 约 117 MiB，包含大量调试信息；这些调试段没有烧入板子。实际烧录的是 8.885 MiB 的 `nuttx.bin`。源码、node_modules、WSL 工具链也不属于 RPK 或设备运行内存。

## 2. 固件主要占用

下表是可相加的实际字节分解；其中系统项包含 ROMFS 元数据与小型配置文件。

| 部分 | 字节 | 容量 | 固件占比 |
|---|---:|---:|---:|
| MiSans-Regular.ttf | 2,594,476 | 2.474 MiB | 27.85% |
| MiSans-Demibold.ttf | 2,577,464 | 2.458 MiB | 27.67% |

两套字体合计 **5,171,940 B / 4.932 MiB，占 55.52%**。它们是系统共享字体，不在 51.61 KiB 的小芽 RPK 内。Regular 用于原生桌面等界面，Demibold 用于快应用粗体文字；不能直接删除而不处理字体引用。

完整 ROMFS 镜像为 5,518,336 B，其中文件内容 5,513,598 B，目录/元数据/填充仅 4,738 B。ROMFS 本身的封装开销不是大头。

| 库 | 已保留部分约占 |
|---|---:|
| GUI 包装与组件库 libgui_wrapper | 574 KiB |
| LVGL（包括部分演示内容） | 425 KiB |
| QuickApp 主运行库 libquickapp | 288 KiB |
| QuickJS | 267 KiB |
| curl | 237 KiB |
| mbedTLS | 160 KiB |
| FreeType | 131 KiB |

还发现约 130 KiB 的 LVGL 演示代码/图片（单个演示头像约 96 KiB）、约 78 KiB 的 Montserrat 内置字体，以及约 44 KiB 的原生示例/测试程序段。它们包含在系统库占用里，不能再次叠加到总固件。删掉测试命令的收益需重编译测量：共享依赖和仍在使用的默认字体不能按表全额扣除。

新增桌面基础功能后，固件从 9,311,424 B 变为 9,316,168 B，**只增加 4,744 B（4.63 KiB）**。秒表、倒计时和锁屏不是固件膨胀的主因。

## 3. 小芽快应用包内部

RPK 最大文件是 `pages/index/index.js`：解压后 169,894 B（165.91 KiB），ZIP 压缩后 42,811 B（41.81 KiB），占整个 RPK 的 81.00%。页面模板、样式和公共模块都打进这个文件。

用 AST 对该文件做互不重叠的字节统计，结果可直接相加：

| 编译后内容（尚未 ZIP 压缩） | 字节 | KiB |
|---|---:|---:|
| 25 个公共业务模块 | 73,783 | 72.05 |
| 页面业务与状态控制 | 41,223 | 40.26 |
| 编译后的界面模板 | 31,856 | 31.11 |
| 编译后的样式，163 条规则 | 22,438 | 21.91 |
| 加载与连接代码 | 594 | 0.58 |

公共模块中较大的部分是动效控制 10,179 B、真实传感器适配 8,655 B、时序后处理 7,553 B、运动引擎 5,336 B、模拟场景 4,283 B。轻量分类器只有 2,248 B，RPK 中没有独立的大模型权重文件。

唯一图片 `common/logo.png` 为 **821 B**。图片不是问题，也没有把 npm 依赖整个打入应用。证书条目压缩后 2,963 B，ZIP/签名容器等其他封装占 4,463 B；其余主要是小型启动代码和 manifest。

原始 `index.ux` 的模板约 18.5 KiB、脚本约 67.7 KiB、样式约 68.4 KiB。构建已经裁剪未使用和被覆盖的样式，编译结果不能再按源码样式大小来估计。各业务模块的 ZIP 压缩共享字典，删除某模块的压缩包节省量不能直接用它的未压缩字节数代替。

## 4. 内存与响应速度

本轮串口 `free`：总堆 8,675,760 B，已用 3,696,376 B，可用 4,979,384 B，历史最大已用 4,646,944 B。未看到内存接近耗尽。

上轮仅桌面启动时堆已用 1,224,784 B；当前小芽已经打开过并保留后台实例，相比增加约 **2.36 MiB**。这个增量包含 JS 运行状态、控件、字体缓存、应用资源等，不能将其全算作 JS 或单独某个页面。已有配置里的 3 MiB 是 JS 堆限制，不代表启动即占满 3 MiB。

目前没有逐对象堆分析，因此不伪造每类运行内存的精确数字。之前交互优化针对页面反复创建、频繁状态更新、模型计算占用执行时间；单纯把 RPK 从几十 KiB 再压小一些，不等于相同比例地提升响应速度。

## 5. 建议的精简顺序

1. **裁剪两套中文字库的字符集合**：容量收益最大，可以保留目前字号和粗体。应覆盖全部静态中文，并考虑以后动态内容可能出现的字；实际节省量要生成子集字体后测量。本次没有生成或替换字体。
2. **去掉未使用的计算器、Lyra ROMFS 示例**：可直接减少约 158 KiB 文件内容，另有少量封装变化。
3. **关闭 LVGL 演示资源和不需要的测试程序**：先整理链接依赖，再保留必要的字体、驱动验证与诊断工具，重编译确认真实收益。
4. **按产品需要裁剪业务模块和系统能力**：动效虽然默认关闭，代码还保留；真实传感器、手机互联等适配代码也仍在。它们影响未来功能，不应为了几 KiB 随意删除。网络和加密库同样要按实际功能依赖决定。

如果目标是让操作更快，仍应同时关注运行时对象数量、绘制成本、JS 调度；如果目标是给固件升级留空间，先处理字库最有效。
